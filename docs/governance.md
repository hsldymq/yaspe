# yaspe Documentation Governance

文档状态：Accepted
最后更新：2026-08-24

## 1. 目标

yaspe 是长期、间歇式演进的项目，工作会跨会话、人员和模型接力。本规范把仓库定义为项目
的持久化记忆，使新的参与者无需依赖旧聊天上下文，也能恢复目标、决定、实现事实、验证证据、
当前断点和下一步。

治理目标是：

- 一个事实有明确权威载体；
- 决定保留背景、候选方案、取舍、后果和重新评估条件；
- 设计完成、代码完成和验证完成始终可区分；
- 当前状态可以被代码、测试和 Git 现实交叉验证；
- 新会话有固定启动协议，旧会话有固定交接协议；
- 文档随决定和实现更新，而不是事后集中补写。

## 2. 文档类型与单一事实来源

### 2.1 Vision

保存项目定位、长期目标、非目标和稳定原则。不保存当前待办、具体 API 或临时实现计划。

### 2.2 Roadmap

保存里程碑依赖、范围、非范围和能力完成标准。Roadmap 以证据推进，不是日历排期。

### 2.3 Living Architecture

保存跨阶段平面、组件职责、依赖方向、ownership、生命周期和长期不变量。它不承担详细讨论
队列，也不把所有未来组件描述成当前实现。

### 2.4 ADR

保存跨组件、长期有效或代价较高的取舍。ADR 接受后保留历史；决定改变时新增替代 ADR，旧
ADR 标记 `Superseded by ...`。ADR 索引见 [decisions/README.md](decisions/README.md)。

### 2.5 Design

保存一个有边界能力的术语、数据流、状态机、API 契约、并发、ownership、失败、保证、验证
要求和开放问题。局部决定可以保存在 Design 的“已接受决定”章节，不必全部拆成 ADR。

### 2.6 Status

保存当前交接快照：当前里程碑、设计/实现/验证三维状态、最近接受决定、开放问题、有序讨论
计划、唯一下一步和最近验证。Status 只摘要并链接权威文档，不复制完整 Design。

### 2.7 代码和测试

代码和自动化测试是“已经实现什么”的证据。代码存在不自动代表语义完整，测试通过也不自动
代表生产故障模型已经验证。

## 3. 三维状态模型

每项重要能力分别记录：

### 3.1 Design Status

- `Open`：问题已识别，尚未形成决定；
- `Discussing`：正在比较方案；
- `Accepted`：当前正式设计；
- `Superseded`：已被新的决定替代。

### 3.2 Implementation Status

- `Not Started`；
- `In Progress`；
- `Implemented`；
- `Removed`。

### 3.3 Verification Status

- `Not Applicable`：实现尚不存在；
- `Not Verified`；
- `Unit Tested`；
- `Race Tested`；
- `Fault Tested`；
- `Workload Validated`。

`Accepted ≠ Implemented ≠ Verified`。Status 和交付说明不得把三个维度合并成一个模糊的
“完成”。

## 4. 决策记录规则

### 4.1 何时写 ADR

满足任一条件时优先写 ADR：

- 改变跨组件职责或依赖方向；
- 影响多个里程碑；
- 未来替换代价高；
- 存在重要备选方案且取舍需要长期保留；
- 涉及外部协调、一致性或公开保证。

### 4.2 何时写入 Design

一个能力内部的接口、状态机、默认值和局部行为写入对应 Design。局部决定仍需记录决定、原因、
主要代价和重新评估条件，但不必为每个命名创建 ADR。

### 4.3 最小决策内容

正式决定至少包含：

- 背景与要解决的问题；
- 已知约束；
- 采用的方案；
- 重要候选方案和不采用原因；
- 正面影响、代价和风险；
- 验证要求；
- 重新评估条件。

被否决方案不能从历史中完全删除。若早期决定只存在于 Design，使用“被替代决定”小节保留
其背景和替代原因。

## 5. 开放问题规则

开放问题必须能被新会话直接继续，不使用只有标题的模糊待办。建议格式：

```text
问题：需要决定什么？
影响阶段：M1/M2/...
已知约束：哪些事实已经接受？
候选方向：有哪些主要方案？
当前倾向：若有，为什么？
前置决定：必须先读哪些 Design/ADR？
完成条件：什么结果代表问题收敛？
```

Status 保存有序摘要和唯一下一步，完整分析进入对应 Design。

## 6. 决策与实现追踪

重要能力需要能沿以下链路追踪：

```text
Decision / ADR
        ↓
Accepted Design
        ↓
Implementation
        ↓
Tests / benchmarks / fault evidence
        ↓
Status
```

实现偏离 Accepted Design 时必须显式处理：修复实现、修订 Design，或新增 ADR 改变决定。不得
让偏离长期停留为未记录的“代码现实”。

## 7. 新会话启动协议

新会话按以下顺序执行：

1. 阅读仓库根目录 `AGENTS.md`；
2. 阅读 [README.md](README.md) 和 [status.md](status.md)；
3. 阅读当前 Roadmap 里程碑；
4. 阅读 Status 指向的正式 Design 和相关 ADR；
5. 检查 `git status`、最近提交、当前代码和测试；
6. 对照文档与仓库现实，识别过期状态或未完成 diff；
7. 开始工作前确认当前里程碑、三维状态、唯一下一步和工作区状态。

若用户的新请求明确替代当前下一步，以用户请求为准，但仍需理解已有决定和未提交修改。

## 8. 会话交接协议

形成正式决定、实现或验证证据后，结束工作前：

1. 更新权威 Design；
2. 按影响更新 ADR、Architecture 和 Roadmap；
3. 更新 Status 的三维状态、最近决定、开放问题和唯一下一步；
4. 链接实现文件和测试证据；
5. 搜索被替代术语、重复规则和冲突表述；
6. 运行 `git diff --check`；
7. 运行与风险相称的测试、race test、benchmark 或 fault test；
8. 在交付说明中报告验证结果和未提交修改。

会话意外中断时，下一会话以未提交 diff、Git 历史、代码和测试交叉验证 Status，不重新开始或
覆盖无法解释的工作。

## 9. 文档更新触发矩阵

| 变化 | 必须更新 |
|---|---|
| 项目定位或长期目标 | Vision，必要时 Roadmap |
| 里程碑范围或顺序 | Roadmap、Status |
| 跨组件职责或长期不变量 | Architecture、ADR、Status |
| 具体能力契约 | Design、Status |
| 重要取舍改变 | 新 ADR 或 Design 替代记录、决策索引、Status |
| 代码实现 | Status、相关 Design 的实现证据 |
| 测试或故障证据 | Status、相关 Design 验证章节 |
| 下一讨论断点改变 | Status |

## 10. 重复与冲突处理

- 完整规则只存在于一个权威文档；其他位置使用短摘要和链接；
- Status 不保存完整设计历史，Architecture 不保存详细工作队列；
- 发现冲突时先停止扩大修改，检查最近提交和 diff，指出冲突的文档与实现；
- 已实现行为冲突由项目决定修实现还是修设计，代理不得仅以“代码已存在”为理由改写设计；
- 不通过删除 ADR、讨论后果或失败证据来制造表面一致。

## 11. 文档质量检查

每次治理性更新检查：

- 链接目标存在；
- 日期、状态和当前里程碑一致；
- Accepted 能力没有被描述成 Implemented；
- 开放问题有约束、权威上下文和完成条件；
- Status 只有一个明确下一步；
- Roadmap 当前范围与 Status 一致；
- 被替代术语没有残留为当前行为；
- `git diff --check` 和相关测试通过。

## 12. 模板

### 12.1 ADR 最小模板

```markdown
# NNNN：标题

状态：Proposed | Accepted | Superseded
日期：YYYY-MM-DD
影响阶段：Mx–My

## 背景
## 约束
## 候选方案
## 决定
## 原因
## 后果
## 验证要求
## 重新评估条件
```

### 12.2 Design 最小模板

```markdown
# NNNN：能力名称

状态：Draft | Accepted | Superseded
最后更新：YYYY-MM-DD
适用阶段：Mx–My

## 目的与范围
## 术语与约束
## 设计
## Ownership 与并发
## 失败、取消与恢复
## 已接受保证与非保证
## 已接受决定及取舍
## 验证要求
## 当前开放问题
## 实现与验证证据
```

### 12.3 Status 必要字段

```markdown
## 当前里程碑
## 当前目标
## 三维能力状态
## 当前代码事实
## 最近接受决定
## 当前开放问题与顺序
## 当前唯一下一步
## 最近验证
## 工作区交接说明
```
