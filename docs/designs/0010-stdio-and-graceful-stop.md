# 0010：stdio Connector 与优雅停止

状态：Accepted（基本行为已接受；公开 API 与 I/O 适配细节待细化）
最后更新：2026-09-11
适用阶段：M1 扩展
依赖：[Source](0003-source-reader-and-admission.md) · [Sink](0005-sink-handoff-and-completion.md) · [Failure](0006-failure-panic-and-shutdown.md) · [ADR-0009](../decisions/0009-separate-graceful-stop-from-cancellation.md)

本文保存标准输入输出 Connector 的记录边界、停止顺序、失败策略与验证要求。
不表示 stdio Connector、命令行入口或显式优雅停止已经实现。

## 1. 定位与范围

支持业务程序把 yaspe 用作输入输出管道，例如：

```sh
cat input.data | yaspe-job | another-command
```

`yaspe-job` 表示使用 yaspe 的业务命令行程序，不表示项目已有该可执行文件。
主要面向工具、实验及允许重跑或放弃结果的场景，不增加持久化、重放、去重或自动恢复机制。
不强制 JSON，也不要求行内内容可被 Connector 解释。业务解析和转换继续由 Operator 承担。

拟使用 `connector/stdio` 承载适配。具体构造函数、记录载体和切分函数签名见 §6 的待定项，
不在实现前复制整套推测性类型声明。

## 2. 输入切分与尾部

### 2.1 已确认的记录边界

- 输入的记录切分可自定义；按行切分作为默认行为，不要求业务数据具有特定格式。
- 切分负责确定记录边界，Operator 负责解释记录内容；自定义分隔符、固定长度或长度前缀
  都可作为切分策略的应用场景，不承诺首版内置所有策略。
- Source 必须使用受控的缓冲衔接非阻塞 Reader；不能把阻塞 stdin 读取直接放进 TryRead。
- 交接后的记录遵守现有 ownership 契约。如果切分结果引用可复用的读取缓冲，必须在交接前
  取得独立存储或转移对应缓冲的 ownership，不能让下一次读取覆盖已交出的数据。

### 2.2 输入结束与残余字节

自然 EOF 或优雅停止结束读取时，Source 将尚未切分的字节和结束标记交给切分函数。
切分函数可以产出最后一条记录、忽略残余字节或返回错误。返回错误仍进入失败流程，
不能伪装为正常结束。默认按行切分时，没有换行符的最后一段作为最后一条记录交付。

已有完整记录以及结束切分产生的记录，都需要遵守容量限制逐步交付，不能为了收尾临时
建立无界队列。无更多记录可交付后才由 Reader 发布永久 finished。
停止读取不承诺处理仍在上游或内核管道中、尚未被 Source 读取的字节。

切分函数在输入结束时如何多次产出记录、如何表示空记录，以及如何拒绝不推进的切分结果，
属于需要进一步明确的协议细节，见 §6。

## 3. 输出与失败

输出面向 stdout，不强制 JSON。输出分隔符和记录类型的具体配置方式尚待确定。
按组串行输出应保留一组内的记录顺序；跨输入顺序仍受 Runtime 并行度保证约束。

已接受的失败策略是：写入或最终 flush 失败后报告错误并停止，不自动重试整组，也不回滚
已经写出的字节。使用者可以重跑或放弃输出，不提供“失败后输出文件仍完整”的保证。
stdout 若使用用户态缓冲，退出前必须处理最终 flush；没有该缓冲时不要求虚构 flush 操作。

这不改变已有 Sink 接管协议：开始外部写入后发生错误，不能回头用全拒返回值声称没有接管。
已接管 items 应通过 reporter 形成符合事实的结果；无法确定完整写出或外部效果的结果不能
报告成功。具体短写、部分记录写出和 flush 错误的逐项映射见 §6，沿用
[Sink outcome 契约](0005-sink-handoff-and-completion.md#14-completion-结果)。

写入完成只说明满足选定输出流的写入确认边界，不等于下游程序已处理、落盘或持久化。
stdio 的简化体现为不恢复、不重试，不体现为忽略 I/O 错误或削弱通用 Sink 的事实报告。

## 4. 优雅停止顺序

### 4.1 已接受的流程

```text
请求优雅停止
  → 停止继续读取 stdin, 关闭本程序持有的输入句柄
  → 将残余字节及结束标记交给切分函数
  → Source 继续交付已有完整记录及尾部切分结果
  → Reader 缓存耗尽后返回 finished
  → Runtime 完成排队和执行中的输入, 输出全部可完成结果
  → flush 输出缓冲, 关闭组件和输出端
  → 程序退出
```

关闭底层输入句柄不等于调用 Source 的最终 Close。前者解除外部读取并进入 drain，后者
属于最终资源清理；直接复用会丢弃缓存的 Close 无法满足上述流程。由停止主动关闭引起的
预期读取错误应识别为停止过程，真实读取错误仍必须报告。

stdio Source 可以关闭本程序持有的 stdin 句柄。该资源不应同时供程序中的其他逻辑继续使用。
终端、普通文件和管道能否通过 Close 或其他取消机制解除阻塞，必须由实际适配验证，
不能从“有 Close 方法”推断任意 Reader 都能被可靠取消。

### 4.2 停止请求与强制取消

第一次 Ctrl+C 请求上述优雅停止，不直接取消用于执行剩余 Operator 的 context。
再次 Ctrl+C 或收尾超时则终止等待。收尾预算从请求停止开始覆盖输入停止、缓存交付、
处理、输出和最终清理，不在 EOF 或阶段切换时重新获得完整时间。

宿主直接取消 Run context 的已有 FailJob 语义继续有效。显式优雅停止入口及 Source 的停止
读取能力需要独立适配，不能通过把现有 cancel 或 Close 偷换含义来实现。
具体 Runtime API、预算配置及重复请求的返回形式尚待细化。

强制取消只意味着不再无限等待，不表示 Go 能强杀任意阻塞 goroutine；进程级退出由
命令行宿主负责。可合作的 I/O 和组件仍需尽可能回收，超时及未完成结果不能报告成功。

## 5. 信号与管道边界

信号由业务命令行入口处理，通用 Runtime 和 Connector 不隐式接管整个进程的信号策略。
在开启作业控制的 Unix 交互式终端里，Ctrl+C 的 SIGINT 通常发送给整个前台进程组，
管道内仍在运行的多个程序都可能收到，并不是沿 stdin/stdout 传递的业务数据。
参见 [Bash 作业控制说明](https://www.gnu.org/software/bash/manual/html_node/Job-Control-Basics.html)。

因此按 Ctrl+C 后，下游可能先退出。优雅停止只能在下游仍可写时输出剩余数据；遇到管道
断开或其他写错误，按 §3 报错退出。不能承诺整条 shell 管道按上游到下游的顺序优雅退出。

命令行入口需要把首次停止请求与后续取消/退出分开；直接将第一次 SIGINT 转为 Run context
取消会触发现有取消语义。Go 的信号适配背景见
[os/signal](https://pkg.go.dev/os/signal)，具体接线须由实现测试验证。

## 6. 实现前待细化项

以下是开放项或候选方案，不能作为已冻结 API 或已验证行为：

| 问题 | 当前约束或候选 | 完成条件 |
|---|---|---|
| 记录类型与输出分隔符 | `[]byte` 及可配置输出分隔符为候选；不限定 JSON | 明确 Source/Sink 的泛型边界、默认分隔符和空分隔符含义 |
| 切分函数接口 | 接收可用字节和结束标记；可产出记录、等待更多输入或报错 | 明确前进量、空记录、EOF 多次切分、非法返回与无进展处理；评估是否采用标准库现有协议 |
| 缓冲与大记录 | 完整记录队列需有界；任意分割可能长时间不产出记录 | 明确未切分字节的容量策略、默认值和超限行为，不默认为已有总字节保证 |
| 输入句柄与取消 | 允许关闭 stdin；最终 Close 与停止读取不同 | 确定支持的平台与句柄类型，验证空闲终端/管道及阻塞读取的退出方式 |
| 输出确认与阻塞写 | 不重试，不能误报成功；当前 Runtime 要求 Accept 返回前报告完整结果 | 明确同步写入/flush 时机、短写及部分失败的逐项结果，以及阻塞写和 broken pipe 的退出方式 |
| 优雅停止入口 | 首次信号停止输入后 drain，再次信号或超时终止等待 | 明确 Runtime/Source 协作接口、预算和并发边界，保持现有 cancel 与 Close 语义 |
| CLI 组织 | 不预建通用配置语言或完整 ETL CLI | 明确首个示例命令、信号接线、日志与业务输出分离及退出状态 |

## 7. 验证要求与实现状态

- 切分：跨读取块的记录、自定义边界、默认无末尾换行、空记录、EOF 残余处理与切分错误。
- ownership 与容量：底层读取缓冲复用不污染已交出的记录，队列满时不扩大预取；超长未切分
  数据按确定后的策略处理。
- 优雅停止：在空闲读取、切分中、队列满、Operator 执行及输出中发起停止，确认完整记录与
  已接管输入在期限内处理完；最终 Close 不提前清空仍应 drain 的数据。
- 失败与升级取消：主动关闭导致的预期读错误不误触发失败，真实 I/O/切分/Operator 错误仍失败；
  再次信号及总期限覆盖所有等待，迟到动作不能改变冻结结果。
- 输出：短写、部分写入、flush 失败、下游提前退出和阻塞写，不重试、不重复报告成功。
- 集成：独立进程和真实管道验证 stdin/stdout、EOF、Ctrl+C 和退出行为；不能只用内存 fake
  证明终端与操作系统 I/O 行为。

实现与验证尚未开始。已有 Runtime 正常 EOF drain 和 context 取消测试不等于显式优雅停止
已实现。测试计划不构成验证通过的证据，动态进度由 [Status](../status.md) 维护。
