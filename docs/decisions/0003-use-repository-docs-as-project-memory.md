# 0003：使用仓库文档保存项目记忆与状态

状态：Accepted

日期：2026-08-24

影响阶段：全阶段

## 背景

yaspe 会跨多轮讨论、多个会话和不同实现者持续演进。聊天上下文不能作为可靠的长期项目
记忆：它可能不可用、被压缩，也无法让代码评审者直接验证。单独维护路线图或零散设计说明，
又不足以区分“已经接受的设计”“已经实现”和“已经验证”，容易让后续接力者重复讨论、误判
进度，或依据过期计划修改代码。

项目需要一套仓库内、可评审、可追踪的接力协议。

## 决定

- 以仓库中的代码、测试和 `docs/` 作为项目事实来源，不依赖聊天记录恢复上下文；
- 使用 [Documentation Governance](../governance.md) 规定文档职责、状态模型、更新矩阵和接力流程；
- 使用 Design 保存完整机制，ADR 保存跨模块且长期稳定的重要决定，Decision Index 索引重要
  局部决定，Roadmap 管理阶段范围，Status 只保存当前快照与唯一下一步；
- 分别跟踪设计、实现和验证状态；`Accepted` 不表示 `Implemented`，也不表示 `Verified`；
- 新会话先读取文档入口和状态，再按当前任务读取权威设计、ADR、代码和测试，并验证仓库现状；
- 决策记录必须包含背景、选择、理由、放弃方案、后果、验证要求和重新评估条件；
- 文档与代码冲突时不得静默选择其一，必须核验并修正过期一方，或明确记录未解决冲突。

## 原因

- 让新的会话、模型或维护者无需原始讨论也能恢复到同一工作位置；
- 保留决定的缘由和代价，避免只记结论后反复推翻或误用；
- 将目标、设计、实现事实、验证证据和下一步分离，减少状态含义混淆；
- 所有项目记忆与代码一起版本化，能够审查、比较和回滚。

## 后果

### 正面影响

- 接力路径明确，当前进度和开放问题可以快速定位；
- 设计变化能够追踪到实现和测试；
- 历史决定被替代时仍保留原因和替代关系；
- 文档陈述可以通过仓库事实和验证命令复核。

### 代价和风险

- 每次重要设计或实现变化都需要同步维护相关文档；
- 同一事实若被复制到多处，仍可能产生漂移，因此摘要必须链接权威来源；
- Status 若未随工作更新，会给下一位维护者造成错误起点；
- 规范本身不能保证执行，需要在每次交付前检查链接、状态和验证证据。

## 不采用的方案

### 依赖聊天记录或会话摘要

不采用。它们不稳定、不可由仓库评审，也不能可靠关联具体代码版本。

### 用一个总文档保存全部信息

不采用。愿景、决策、详细机制、计划和实时状态变化频率不同，混在一起会造成重复、过期和
接力阅读成本上升。

### 只使用 issue 或任务列表

不采用。任务列表适合追踪工作项，但不能替代完整的设计理由、长期保证和仓库内实现事实。

## 验证要求

- 新接力者仅根据仓库文档能指出当前阶段、已实现能力、开放问题和唯一下一步；
- 重要决定可从 Decision Index 定位到包含理由与取舍的权威记录；
- Roadmap、Status、Design 和代码状态不使用同一个模糊的“完成”概念；
- 文档相对链接有效，交付前记录实际执行过的验证；
- 抽查实现变化时，能够找到对应设计条款和测试证据，或明确标记尚未实现/验证。

## 重新评估条件

- 仓库规模或贡献者数量使当前手工索引无法可靠维护；
- 引入能够成为权威来源的自动化规格、issue 或发布系统；
- 文档检查可以自动生成状态矩阵或决策索引；
- 实践证明当前拆分导致持续重复，或新接力者仍无法无歧义恢复工作。
