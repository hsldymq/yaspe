# 0009：区分优雅停止请求与强制取消

状态：Accepted
日期：2026-09-11
影响阶段：M1 扩展及后续 Runtime/Connector 生命周期

## 背景

stdio 管道程序需要在停止接收输入后处理剩余记录并写完输出。现有 Runtime 的宿主 context
取消会停止 admission 和 Operator 处理；Source 最终 Close 可以丢弃未交接缓存。直接用任一
操作表示优雅停止，会损失本来需要完成的输入和输出。

## 决定

- 优雅停止与宿主 context 取消使用不同的语义入口，具体 API 留在实现设计中确定。
- 优雅停止先终止外部读取，再交付 Source 缓存与切分尾部，最后处理排队/执行中的输入并
  完成输出和清理；底层输入句柄关闭与 Source 最终 Close 分开。
- 命令行首次 Ctrl+C 请求优雅停止，再次 Ctrl+C 或收尾期限到期终止等待。信号策略属于
  命令行宿主，不由库隐式修改进程级信号处理。
- 所有收尾阶段共享从停止请求开始的总预算。原有 context 取消、真实失败及超时 fence
  语义保留，优雅停止不把真实 I/O 或处理错误改成成功。

详细 stdio 行为、尾部切分、失败边界与开放项见
[stdio Design](../designs/0010-stdio-and-graceful-stop.md)。

## 取舍与后果

优点是工具程序可以尽量完成已有工作，同时保留明确的取消升级路径。代价是 Runtime 与
Source 需要额外的停止读取协作能力，不能只调整信号监听代码；句柄所有权、阻塞 I/O 与
停止竞争需要真实验证。

不采用第一次 SIGINT 就取消 Run context，因为它会取消本来需要继续的处理；不采用先调用
最终 Source.Close，因为清理缓存与 drain 目标不同；不采用无限等待所有输出，因为下游可能
已经退出或永久阻塞。无法写完时仍按已接受的失败策略退出，不自动重试。

## 验证与重新评估条件

验证输入停止、缓存交付、处理、输出和关闭的顺序，首次/再次信号以及总预算竞争；必须
覆盖真实管道的阻塞与下游退出。当前没有实现或验证完成的声明。

其他 Source 的停止读取语义、跨平台终端支持或进程托管方式改变时，重新评估协作接口与
信号接线，但不能默默改变已有取消和最终 Close 的含义。
